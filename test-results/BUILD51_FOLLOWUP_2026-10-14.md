- **Issue #162:** Chrome issue evidence reports 7,939/4,386 ms startup, including 7,876/4,333 ms controller initialization; neither request had a prepared opening. Public text manifests use two-second segments, but list the highest bitrate first (up to 7.26 Mbps). All variants remain accessible to native adaptation; cold requests do not receive prepared-opening or reduced-buffering flags. Existing completed-opening fast start remains unchanged. Physical testing also exposed a 20-second wait behind an overlapping native request. The proxy now waits at most 120 ms for existing work, then redirects that native request to the validated public CDN rather than queuing behind a stalled reader. A stalled-producer regression confirms this bound. No extra player or speculative downloader is added. The passing physical profile run below is encouraging; store-release and varied-network performance remain acceptance gates.
- **Both video queues:** initialize Feed and Trending metadata on entry to the video experience. Active next-two preparation retains priority and the existing 8 MiB RAM limit. The other tab's return video and following two enter the existing disk queue before farther active-tab videos. The queue is deduplicated and capped at eight; one speculative downloader, approximately 200 MB disk allowance, Wi-Fi/device guards and 50 MB/day extra budget remain. No second player. Data Saver, constrained networks, user storage settings and OS scheduling can prevent preparation; instantaneous switching is not guaranteed.
- **Refresh:** Feed/Trending vertical-dots menu includes Refresh above Report a bug. Manual refresh is coalesced and has a five-second client cooldown. Backend user quotas remain authoritative for modified clients.
- **API protection:** shared Redis limits before authenticated DB work, per-user action and burst budgets, shared public IP/IPv6 subnet and auth/OTP destination budgets, and a dedicated diagnostics allowance. Changing IP or hitting another API replica does not reset authenticated quotas. `429` includes `Retry-After`; staging/production fail closed with retryable `503` when Redis is unavailable. Development alone can use an in-memory store when Redis is deliberately disabled.
- **Critical audit finding:** removed the legacy unauthenticated `/payments/:id/mark-paid` route, which called wallet-credit logic without payment-provider verification.
